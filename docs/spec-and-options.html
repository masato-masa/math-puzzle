式をどこに置くか

現行仕様（v2）を確定させたうえで、「途中でできる数字＋演算子タイルがいまいち」という 引っかかりを起点に、コアメカニクスの代案を並べて比較する。決めるのは 式をどこに持たせるかの一点で、それ以外の要素はどの案でも流用できる。

  • POC = HTML/JS（動作中）
  • 検証ツール = Python ソルバー
  • 収録 12 レベル ／ par 3〜12
  • 本実装 Flutter = 未着手

仕様

現行仕様 v2

すべてソルバーで検証済みの状態。以下がいま実際に動いているルールで、 レベルデータ・POC・検証ツールの三者で一致している。

盤とタイル

要素仕様
盤N×N の正方グリッド（現行 3〜4）。壁マスを任意に配置できる。
タイルトークンの配列。トークンは数値または演算子。
[8] ["÷", 4] [8, "÷", 4]
演算子二項 + − × ÷ ^／前置 √（直後の数に作用）／後置 !（直前の数に作用）
通常タイル上下左右へ 1 マス動く。
固定タイル自分からは動けない。ぶつけられる側にはなれる。
滑るタイル壁・盤の縁・結合できないタイルに当たるまで一気に進む。まとめて 1 手。
出口盤の縁のマス＋外向き。固定値または範囲を指定。トークン 1 個の数値タイルだけが通れる。

結合と計算

動かした側を mover、動かされた側を target と呼ぶ。 mover の末尾 と target の先頭 が 数字↔演算子で噛み合うときだけ結合でき、数字どうし・演算子どうしは弾かれる。 連結順は必ず mover が前、target が後。 この非対称性が「8 を ÷4 にぶつけると 8÷4、逆はできない」を生んでいる。

結合後、単項演算子（√ ・ !）を先に簡約し、構造の妥当性を確認したうえで、 両端が数値なら左から順に計算する（優先順位なし）。 割り切れない除算などで計算が成立しない場合は、結合そのものが起きなかったことになる。

勝敗と手数

  • クリア条件：数字を含むタイルが盤上から全て無くなること。演算子タイルは余らせてよい。
  • 手数：移動・結合・出口からの排出をそれぞれ 1 手として数える。Undo あり。
  • 検証：全状態探索で、クリア可能性・最短手数・解法の数・詰み手・「作れるのに出せない値」・一方向だけで解けないか・使われない行や列がないかを毎回チェックしている。

論点

いま引っかかっている 2 点

「結合後、氷効果がなくなるのが効果として弱いかも」
「数字ブロックと演算子ブロックを分けているので途中で数字＆演算子ブロックができるが、これがいまいち」

後者はメカニクスの根に触れている。現行方式では、式がタイルの内側に文字列として蓄積されるため、 プレイヤーは盤面を見るだけでなく各タイルが何をどこまで抱えているかを記憶し続ける必要がある。 3 + のような中間状態は、盤面上では「まだ何でもない物体」で、 読む負荷だけを増やして意思決定の材料になっていない。引っかかりの正体はここだと考えている。

前者（滑るタイル）は独立した小さい論点なので、後半でまとめて扱う。

案

式をどこに置くか — 3 つの案

メカニクスの違いは結局「式という情報をどこに保持するか」に集約される。 タイルの中（現行）、タイルの辺、盤面の並び、の 3 通り。

現行A

式はタイルの中（トークン連結）

数字ブロックと演算子ブロックが別々にあり、ぶつけると内部の配列が連結される。 両端が数字になった時点で計算される。

得
3 項以上の長い式が自然に作れる。ぶつける順序がそのまま式の順序になる。
損
中間状態が「読めない物体」になる。「ぶつけた側が前」という規則が盤面に現れず、覚えるしかない。演算子ブロックが場所を取り、盤面が混む。
案B

式は数字タイルの辺（提案されている案）

数字タイルの 4 辺のうち任意の辺に演算子を付ける。ぶつかったとき、 接触する 2 辺のうち片方だけに演算子がある場合に限りその演算子で計算する。 両方にある／どちらにも無い組み合わせはぶつかれない。ぶつけた側が左辺になる規則は現行のまま維持できる。

得
盤面上の物体が常に「数字」なので一目で読める。どの向きから当てるかが主要な資源になり、滑る・押すギミックと強く噛み合う。演算子が独立ブロックとして場所を取らない。
損
1 回の衝突が 1 個の二項演算に限られる（ただし多段の式は衝突を重ねれば表現できるので、実質の表現力は現行と大きく変わらない）。辺の向きが固定なので配置の自由度は下がる。
案G

式は盤面の並び（隣接した行を式として読む）

数字と演算子は別ブロックのまま、タイルは連結しない。縦横に連続した並びが 完成した式として読めるようになった時点で、その並びが 1 つの数字に潰れる。

得
式が文字通り盤面に見えている。「ぶつけた側が前」という見えない規則が消え、左から右の並びがそのまま順序になる。長い式も作れる。
損
1 手では式が完成せず、ブロックを並べる作業感が出やすい。盤面を広く使うので 3×3 では窮屈になり、盤が大きくなると検証コストも上がる。

案Bで決めるべき細部

案Bを採るなら、接触の可否だけは早めに固めておきたい。以下が骨格で、 これが決まればソルバー側もそのまま書き換えられる。

  • Q1計算後の辺はどうなるか。 ぶつけられた側の未使用の辺だけを残すのが素直。両者の残り辺を合成すると、 辺が増え続けて盤面が読みにくくなる。
  • Q2回転を許すか。 「回転 1 手」を入れると、駒の種類を増やさずに動詞が 1 つ増える。 許さない場合は配置の妙が全てになり、難度は上がるが詰みやすくもなる。
  • Q3演算子ブロックを併存させるか。 案Bに寄せるなら廃止した方がよい。併存させると読みやすさという利点が薄れる。
  • Q4√ と ! はどう置くか。 単項演算子は二項と性質が違うので、辺ではなく「盤面のマス」（通ると作用する）に置く方が収まりがよい。

論点

滑るタイルをどう持続させるか

現行は「ぶつけられた側の性質を引き継ぐ」ため、滑るタイルを他にぶつけた瞬間に効果が消える。 弱く感じるのはその通りで、選択肢は以下。

案ルール効いてくるところ
現行ぶつけられた側の性質を引き継ぐ実装は単純だが、効果が 1 回で消える
継承ぶつけた側の性質を引き継ぐ「滑る性質を相手に移す」動きが生まれる
伝染どちらかが滑るなら結果も滑る進むほど盤面が滑りやすくなり、終盤が自然に難しくなる
床属性タイルではなくマスを氷にする。氷マスに入った物は滑る継承の問題が消え、壁と同じくレベルデザインの道具になる

床属性を基本にするのが筋が良いと考えている。滑るかどうかがタイルの素性ではなく 場所の性質になるため、「結合したら消えるのか」という問いがそもそも発生しない。 壁と同じ語彙で語れるので、レベル生成器にもそのまま組み込める。 タイル側の性質として残したい場合は「伝染」を併用すると効果が持続する。

提案

次にやること

案B（辺に演算子）を主軸に v3 プロトタイプを作り、現行Aと同じ題材で比較する。 案Bは中間状態を消したうえで、「どの向きから当てるか」という現行に無い判断を持ち込む。 滑る・押すといったギミックとも噛み合い、滑りは床属性に移す。 案Gは「長い式を見せたい」となった場合の対抗案として残す。

比較のやり方

既存の Python ソルバーはルール部分が分離してあるので、結合判定だけ差し替えれば 案Bの盤面もそのまま検証できる。同じ計算内容（例：24 ÷ (7 − 3) = 6）を A と B の両方で組み、同じ指標で並べれば、感覚ではなく数字で選べる。

  1. 結合判定を差し替えた案B版ソルバーを用意する
  2. 同じ題材のレベルを A / B それぞれで作り、最短手数・外れ手・詰み手・ひっかけの数を比較する
  3. POC に案Bモードを足し、実際に触って「一目で読めるか」を確認する
  4. どちらで行くか決めてから Flutter の本実装に入る

本実装を止めているのは正しい判断で、コアメカニクスが決まる前に Dart へ移植すると、 決め直しのたびに二重に作業が発生する。逆に、ここが決まればルールとレベルデータは すでに検証済みの資産として、そのまま移植できる。
